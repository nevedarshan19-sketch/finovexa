# FINOVEXA free production stack

Status: staging verified 2026-11-03. **Not deployed.** The existing Render service
and its data stay untouched until this runbook is executed with explicit approval.

## 1. Chosen architecture

| Layer | Service | Plan | Why |
| --- | --- | --- | --- |
| API + web UI | Render Web Service (Docker, `render.yaml`) | Free | Already hosts the app; FastAPI serves the built SPA on one origin |
| Database | Neon Postgres | Free | Managed Postgres with no card, survives redeploys |
| Uploaded files | Postgres table `stored_files` (`FILE_STORAGE=database`) | — | No disk needed; survives redeploys and restarts |
| DNS / CDN | Optional Cloudflare Pages | Free | Only if a separate static frontend is wanted; not required |

A single process serves `/api/*` and the SPA, so there is no CORS split and no second
deployment to keep in sync.

Rejected during the zero-cost evaluation:

- **Cloudflare Python Workers** — 10 ms CPU per request cannot cover PBKDF2 password
  hashing (measured ~38 ms), and the FastAPI app exceeds the worker bundle model.
- **Cloudflare D1** — not SQLAlchemy/psycopg compatible without a rewrite.
- **Cloudflare R2** — requires a payment method; excluded by the no-card rule.
- **Render persistent disk** — paid plan only.

## 2. Free-tier limits that shape the design

Checked 2026-11-03. Re-check the provider pages before deploying; free terms change.

| Limit | Render Free | Neon Free |
| --- | --- | --- |
| Cost / card | $0, no paid plan on this account | $0, no credit card |
| Compute | 0.1 CPU, 512 MB RAM, 750 instance hours/month | 100 CU-hours/project/month |
| Sleep | Spins down after ~15 min idle; cold start 30–60 s | Compute suspends ~5 min after the last connection closes |
| Storage | No persistent disk | 1 GB/project, 20 GB across up to 100 projects |
| Recovery | Redeploy logs only | 6-hour restore window, 1 GB of changes |
| Over-limit | Service stops/suspends | Compute suspends or operation fails; no auto-charge |

Consequences:

- There is no background worker. All reminders, aging and forecast values are computed
  on request, so a sleeping service simply shows fresh data on the next visit.
- Uploads are capped by `ACCOUNTING_MAX_UPLOAD_MB` (default 10) to protect the 1 GB
  database allowance.
- 750 Render hours is enough for one service. Do not create a second free service in the
  same workspace without checking usage.
- **Do not add an uptime pinger.** Keeping Render awake 24/7 also keeps a Neon connection
  open, which can burn through the 100 CU-hour monthly allowance. Let the service sleep;
  the cold start is the price of staying inside the free tier.

## 3. Database setup (Neon, no card)

1. Sign in at https://neon.com (Google/GitHub is fine; no billing details).
2. Create one project in the region closest to the Render service. Do not create extra
   branches; each branch has its own storage.
3. Open **Connect** and copy the **pooled** connection string. It looks like:

   ```
   postgresql://USER:PASSWORD@ep-xxx-pooler.REGION.aws.neon.tech/DBNAME?sslmode=require
   ```

4. Keep it for the Render environment; never write it into the repository.
5. Optional hardening: create a second, non-pooled URL for manual `pg_dump` runs.

The app normalizes `postgres://` and `postgresql://` to `postgresql+psycopg://` and
creates all tables plus additive upgrades on first start.

## 4. Render setup

Create a **new** service; do not modify the existing deployment.

1. Render Dashboard → New → Web Service → same repository/image.
2. Runtime: Docker. Dockerfile: `./Dockerfile`. Health check: `/api/health`.
3. Instance type: **Free**.
4. Environment variables — the full list is in `render.yaml`. Required values:

   | Variable | Value |
   | --- | --- |
   | `ENV` | `production` |
   | `SECRET_KEY` | generated by the blueprint, kept stable forever |
   | `DATABASE_URL` | Neon pooled URL (secret) |
   | `FRONTEND_URL` | the public service URL, e.g. `https://finovexa.onrender.com` |
   | `FILE_STORAGE` | `database` |
   | `AUTO_SEED` | `false` |
   | `DEMO_RESET_ENABLED` | `false` |
   | `PAYMENT_DOCUMENT_KEY` | Fernet key (see §6), keep stable |
   | `DEVELOPER_NAME` | display name for the platform developer |
   | `DEVELOPER_EMAIL` / `DEVELOPER_PASSWORD` | the only login provisioned at startup (secret password) |

   Production currently boots with **developer-only bootstrap**: no `INITIAL_*` values are
   set, so the first start creates exactly one account — the developer. That account signs
   in at `/developer/login` and creates the owner, employee, senior accountant and junior
   accountant logins from the console, then can reset their passwords, rename emails and
   disable or re-enable them.

   The developer password must be at least 12 characters with a letter and a digit. It is
   used only when the developer account does not exist, is never logged, and never
   overwrites an existing account. Leave both developer values blank to disable the
   console — but then no account exists at all.

   The older `INITIAL_OWNER_*`, `INITIAL_BUSINESS_NAME` and accountant `INITIAL_*`
   variables still work if you ever want startup provisioning. They are intentionally not
   declared in `render.yaml`. Leave them unset for developer-only bootstrap.

5. Deploy and read the first log line:

   ```
   FINOVEXA API started · env=production · demo_seed=False · initial_accounts=none · developer_console=configured · ...
   ```

   `initial_accounts=none` is expected with developer-only bootstrap. On later boots the
   developer account is left unchanged.

6. Sign in at `/developer/login` and create the first owner login from the console.

7. Do not enable `AUTO_SEED` or `DEMO_RESET_ENABLED`. Even if `AUTO_SEED=true` leaks into
   production, `ENV=production` skips the demo seed and logs a warning.

## 5. Account creation after first boot

| Role | How it is created | How the login is edited |
| --- | --- | --- |
| Developer | Only from `DEVELOPER_EMAIL` + `DEVELOPER_PASSWORD` in the backend env | Environment only; never editable in the console |
| Owner | Developer console → Add login | Developer console (email, name, password, disable) |
| Employee | Developer console → Add login (attach to an owner) | Developer console |
| Senior / junior accountant | Developer console → Add login | Developer console |
| Customer | Senior accountant onboards a client; the customer login is issued there | Developer console can reset password, rename email or disable the login |

Owner and employee logins can also still be self-created through the existing owner
registration and owner Team page when that is preferred. The developer console is the
break-glass path that can create and repair every non-developer login.

No demo owner, demo employee or demo business records are created in production.

## 6. Secrets that must never rotate silently

- `SECRET_KEY` signs sessions. Changing it signs everyone out; that is acceptable.
- `PAYMENT_DOCUMENT_KEY` encrypts Payment Connect statement originals. If it is blank,
  the key is derived from `SECRET_KEY`, so **rotating `SECRET_KEY` then makes old
  statement blobs unreadable**. Set an explicit key and keep it stable:

  ```bash
  python -c "import base64,secrets;print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode())"
  ```

- Losing either key does not affect invoices or ledger records, only encrypted blobs.

## 7. Backups and recovery

Neon Free keeps a 6-hour restore window (1 GB of changes). That covers accidents, not
long-term retention. Take an encrypted logical dump outside the repo after go-live and
before risky changes:

```bash
# Custom format, no owner/ACL statements so it restores into any role
pg_dump "$DATABASE_URL" --format=custom --no-owner --no-acl --file=finovexa-$(date -u +%Y%m%dT%H%M%SZ).dump

# Verify by restoring into a scratch database
createdb finovexa_verify
pg_restore --dbname=finovexa_verify --no-owner --no-acl finovexa-latest.dump
psql finovexa_verify -c 'select count(*) from users; select count(*) from invoices;'
```

The repository's `backend/scripts/backup_db.py` is SQLite-only (AES-GCM snapshot plus
integrity check) and is not used with Neon.

Uploaded files live in `stored_files`, so a database dump includes them.

## 10. Rollback

The new service is additive. Until DNS or the frontend points at it, rollback is simply
leaving the old service in place and deleting the new service after review. Do not
delete the Neon project while it holds the only copy of new uploads.

## 11. Known limitations

- Cold start after 15 idle minutes: the first page load can take 30–60 s.
- 512 MB RAM: large PDFs or bulk imports may need smaller batches.
- No persistent disk: `FILE_STORAGE=local` must never be used on Render.
- No scheduled jobs: emails/SMS are sent only by explicit request paths.
- Free terms can change; re-verify before every new deployment.
